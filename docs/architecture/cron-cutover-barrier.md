# Scheduler deployment cutover barrier

The barrier closes new Python cron admission and records deployment evidence. It does
not authorize Rust execution until a trusted deployment verifier has proved the old
deployment drained. No such verifier or activation command is supplied in this batch.
The cloud production gate remains closed.

## Persisted state

The existing `agistack_cron_scheduler_owners` global row owns three additive fields:

| Field | Meaning |
| --- | --- |
| `cutover_phase` | `unverified`, `prepared`, `blocked`, or verifier-owned `verified` |
| `cutover_revision` | Compare-and-swap revision for this deployment boundary |
| `cutover_evidence` | Versioned manifest, append-only receipt log, and last DB observation |

Migration `7c90e5134285` defaults every existing owner to `unverified`; it does not
delegate ownership or manufacture historical evidence. It was autogenerated against
an isolated PostgreSQL baseline and reviewed to include phase/revision constraints.
Downgrade preserves active evidence by refusing prepared, observed or Rust-owned rows.
A pristine upgrade can be reversed without changing the previous owner.

`prepare` locks this row, checks the expected revision and a Python/off source owner,
then sets `owner_kind=draining`. It preserves `owner_epoch` and existing admission
capabilities. Already admitted executions can finish or resume with their exact nonce.
New Python admission is denied after the transaction commits. This does not stop an
old binary that predates admission fencing, nor does it remove APScheduler schedules.

`record-receipt` appends observations bound to the exact deployment, source generation
and declared participant. Reusing a receipt id with different data is rejected. A
receipt saying `closed` remains unverified; it cannot change the owner or phase to
`verified`. No raw logs, execution payloads, credentials or arbitrary boolean flags
are accepted by the receipt protocol.

`observe` records database blocker counts and the database observation time, and
persists `blocked`. Counts include active admissions, legacy runs without matching
full-scope admissions regardless of their reported success, nonterminal canonical
Agent runs, pending/answered HITL requests, and retained HITL snapshots regardless
of expiry. The scan covers the global deployment scope conservatively; unrelated
ordinary runs may appear when old cron execution cannot be safely correlated.
These are diagnostics, not a complete historical inventory or an atomic proof of
cluster quiescence. Even all-zero counts leave `deployment_verifier_unavailable`.

## Operational commands

Run from the repository root with its configured database. `inspect` is read-only;
the other commands persist the explicitly requested preparation/observation.

```sh
PYTHONPATH=. uv run python scripts/cron_cutover_barrier.py inspect
PYTHONPATH=. uv run python scripts/cron_cutover_barrier.py prepare \
  --manifest-file deployment-inventory.json --expected-revision 0
PYTHONPATH=. uv run python scripts/cron_cutover_barrier.py record-receipt \
  --receipt-file deployment-receipt.json --expected-revision 1
PYTHONPATH=. uv run python scripts/cron_cutover_barrier.py observe --expected-revision 2
```

Use the returned revision for the next mutation. There is no `finalize`, `force`,
`verified=true`, direct SQL activation, or automatic timeout override.

An inventory follows the structural `cron-deployment-inventory.v1` protocol:

```json
{
  "protocol": "cron-deployment-inventory.v1",
  "deployment_id": "deployment-identifier",
  "source_generation": "existing-python-generation",
  "target_generation": "candidate-rust-generation",
  "participants": [
    {"kind": "producer", "participant_id": "scheduler-instance-identifier"},
    {"kind": "queue", "participant_id": "queue-boundary-identifier"},
    {"kind": "execution", "participant_id": "execution-identifier"},
    {"kind": "hitl_resume", "participant_id": "resume-authority-identifier"}
  ]
}
```

The inventory must come from actual deployment discovery. This example is a shape,
not a claim that these four participants constitute a complete live deployment.

A `cron-deployment-drain-receipt.v1` observation contains `receipt_id`,
`deployment_id`, `source_generation`, the exact `participant` object, `observation`
(`closed` or `unresolved`), and a lowercase SHA-256 `evidence_sha256`. The external
artifact remains outside the owner row. Both protocol parsers reject unknown fields.

## Required two-phase deployment integration

The subsequent deployment verifier must implement the following ordering:

1. Establish a complete deployment inventory and a durable boundary for every old
   scheduler producer, execution worker, dispatch queue and HITL resume authority.
   A single process list or a local scheduler stop is not a cluster boundary.
2. Commit `prepare` before removing schedules or stopping current producers. Collect
   positive closure acknowledgements for every old producer, including binaries
   that do not check the owner row. Reconcile/remove only the recorded cron schedule
   ids through APScheduler APIs; do not wipe a shared scheduler datastore.
3. Allow exact admitted execution and HITL capabilities to settle. Account for every
   old queued or executing request and every retained/answered resume. Unknown
   delivery, absent correlation, a vanished worker, or incomplete deployment roster
   leaves the boundary blocked. If ordinary execution cannot be correlated to cron,
   the deployment integration needs a broader intake/drain boundary rather than a
   guessed classification of message text.
4. Verify external closure artifacts and current DB blockers against the same
   prepared revision. Produce the trusted receipt described by
   [the verification schema](cron-cutover-verification-v1.schema.json). Its digests
   identify the canonical inventory and closure evidence, and its deployment id and
   revision must match the owner row. Only that future trusted writer may atomically
   persist `verification`, mark `verified`, and delegate `owner_kind=rust`.
5. Rust acquisition still checks there are no active legacy admissions. Owner
   acquisition/renewal/current checks and control, operation and scheduled-fire
   admission transactions share the structural verification predicate. Revoking the
   phase or changing its revision fences further admission. Exact lease release
   remains available for cleanup after revocation.

`CronJobRun.success` from the old dispatcher does not prove execution stopped.
Redis running/finished TTL expiry, HITL snapshot expiry, empty admission tables,
owner lease expiry, wall-clock grace periods and process restart do not supply the
missing historical proof. This release never turns those observations into a
semantic judgment or an activation decision.

## Remaining work

- Connect the real deployment control plane and obtain a representative, complete
  multi-worker inventory plus signed/authenticated closure artifacts. The required
  external sample and verifier are not available in this repository batch.
- Implement controlled APScheduler producer shutdown/removal and the authenticated
  verification writer. Define an audited abort/rollback protocol before using a
  prepared deployment in production; dropping barrier evidence is not rollback.
- The [continuous Rust owner lifecycle](cron-owner-lifecycle.md) now renews control
  ownership independently of admitted work and preserves separate run leases.
  This local lifecycle does not supply the missing deployment drain evidence.
- Gate backward delegation until Rust operations, ordinary Agent executions and
  HITL resumes have real terminal/closure evidence. A local worker's stopped state
  does not mean its durable waiting work has drained.

Tests use synthetic verifier receipts only inside private schemas or dedicated
unmigrated test databases. Their fixture helper refuses to write such evidence into
a migrated shared schema. They validate protocol fencing, not deployment readiness.
